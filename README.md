# External Link Manager（外部引用管理）

管理 Obsidian 笔记里指向**仓库外部**（磁盘绝对路径）的文件 / 文件夹链接。

针对的典型场景：笔记里写了

```markdown
[启动参数](C:\Users\me\Desktop\启动参数.txt)
```

这种链接 Obsidian 不会帮你维护——文件被移走、或者你换了用户名，链接就悄悄失效了，而且 `git` 也追踪不到仓库外的东西。本插件负责盯着它。

---

## 功能

| 需求 | 实现 |
| --- | --- |
| 外部文件被移动 → 自动更新笔记里的链接 | 按文件名在监控目录里找新位置，配合「目录包含关系 + 路径后缀重合度」打分，高置信度唯一候选自动改写；多候选则列出让你选 |
| **外部文件只改了名、内容没变 → 靠内容指纹认出来** | 给链接引用到的文件记录 SHA-256 指纹。文件被改名后即使名字完全对不上，也能靠「大小相同 + 指纹一致」精确认出 |
| 外部文件/文件夹被改名（`file1` → `file11`、`xxx.txt` → `xxx1.txt`） | 名称对不上时用「名称相似度 + 父目录重合度」匹配，命中后提示 `名称相似 0.95（疑似改名）`。**文件和文件夹都参与** |
| 用户名变更（`C:\Users\旧名` → `C:\Users\新名`） | 内置重映射规则，命中且文件存在就直接改写 |
| 指定要监控的外部文件夹 | 设置页可增删，支持递归；`fs.watch` 实时监听，文件增删改后自动核对 |
| 手动 / 自动更新 | 总开关 + 「打开笔记时」「外部变动时」「定时扫描」三个独立开关；也可随时点「修复可修复项」 |
| **推荐列表：每条失效链接列出多个候选让你挑** | 「修复可修复项」→ 一次性列出全部待修复项及各自的推荐列表，逐条选后批量应用；「重新指向」→ 单个链接的推荐列表 + 手动浏览/输入兜底 |
| 总览所有 Markdown ↔ 外部文件的映射，可增删改 | 「外部引用管理」面板：状态 / 笔记 / 链接文本 / 当前路径 / 说明 / 操作；新增、编辑、重新指向、删除、忽略全部同步回笔记 |
| **自动检测不擅自改笔记，等你确认** | 外部文件改名/移动后，插件只把链接标成「待确认」，绝不自动写。点行内「确认更新」或顶部「确认全部待确认项」才落地。也可一键关掉这个确认要求 |
| **只在你指定的文件夹里找，不碰系统其它位置** | 插件只有一个范围：你配置的监控文件夹。推荐列表里绝不会冒出桌面/文档里碰巧同名的文件，也不会去遍历用户主目录拖慢系统 |
| **一眼看出哪些引用在「范围外」** | 扫描仓库时，笔记里存在外部链接但目标不在监控文件夹内 → 标成「范围外」。面板每行都有范围标记，顶部筛选可按「监控文件夹内 / 外」过滤，CSV 也带这两列 |
| **链接匹配规则可看可改** | 抓链接的正则开放成设置项，带实时体检和「试一下」（粘一段 Markdown 就能看到哪些会被识别、哪些被跳过）。规则写坏会自动退回默认，不会让插件挂掉 |
| **监控不拖慢你改文件** | 监听回调只入队、无锁事件队列、外部变动不重读笔记、只搜变动目录、限流落盘 —— 详见 [不干扰外部文件的正常读写](#不干扰外部文件的正常读写) |

## 安装

1. 把 `obsidian-external-link-manager` 整个文件夹复制到 `<你的仓库>/.obsidian/plugins/` 下，并重命名为 `external-link-manager`
2. Obsidian → 设置 → 第三方插件 → 关闭「安全模式」（如未关闭）→ 刷新 → 启用 **External Link Manager**

本插件是免编译的（纯 CommonJS），不需要 `npm install` / `npm run build`。

> 仅支持桌面端（需要访问文件系统），`manifest.json` 里已标记 `isDesktopOnly: true`。

---

## 快速上手

1. 设置 → External Link Manager → **监控的外部文件夹** → 添加你要盯的目录（例如 `D:\资料`、`C:\Users\你\Desktop`）
2. 点侧边栏的 🔗 图标（或命令面板搜「外部引用管理」）打开面板
3. 点「扫描」→ 面板列出全库所有外部引用及其状态
4. 之后外部文件一变动，插件会自动核对；失效的会变成「可修复」，高置信度的直接改好

## 面板说明

**状态**

| 状态 | 含义 |
| --- | --- |
| 正常 | 目标文件当前存在 |
| 可修复 | 原路径不存在，但找到了唯一的新位置（鼠标悬停看相似度；说明栏会写「疑似被改名」还是「按文件名匹配」） |
| 多个候选 | 找到多个同名 / 相似文件，需要你点「选择…」确认 |
| 文件丢失 | 找不到任何候选 |
| 已忽略 | 你手动忽略，不再提示 |

**操作按钮**

- `打开` / `定位` — 用系统默认程序打开外部文件 / 在文件资源管理器中显示
- `应用` — 把笔记里的链接改到推荐度最高的位置
- `重新指向` — 打开推荐列表弹窗（见下）
- `编辑` — 改链接文本、目标路径、备注（写回笔记）
- `忽略` — 不再提示该条
- `删除` — **整条链接一起删除**（`[显示文字](路径)` 全部删掉，不留纯文本残渣）。如果这一行只有这条链接，整行一并删除，并自动合并因此产生的多余空行；如果行内还有其他内容，则只摘掉链接并清理连接处的多余空格

### 推荐列表

**「修复可修复项」**（工具栏）：把所有待修复项一次性列出来，每条卡片里是该链接的**全部推荐候选**（分数 + 理由 + 路径），默认勾选推荐度最高的那个。你可以改选别的、或勾「跳过这条」、或点「手动重新指向…」。最后点「应用选中的 N 项」才写回笔记 —— **不点就不会动你的笔记**。

**「重新指向」**（每行操作）：

1. **推荐新位置** — 候选列表，每条显示置信度和理由（`内容完全相同（指纹一致）` / `文件名一致` / `名称相似 0.95（疑似改名）`），点「应用」立即生效
2. **重新计算** — 重新跑一遍候选搜索（比如你刚把文件移回来）
3. **手动指定** — 输入框 + 「浏览…」按钮，自己挑一个；也可以直接从系统把文件/文件夹**拖进输入框**

**工具栏还有「一键修复高置信度」**：只应用「置信度达标且并列最高分唯一」的候选，不做任何猜测。适合日常无脑点一下。

**其他**

- 「新增映射」：笔记选择框支持**输入关键字实时检索**（文件名、路径、中文子串都能搜），不再是几百项的原生下拉；默认填入当前打开的笔记
- **「外部路径」支持拖拽**：从系统「文件资源管理器 / 访达」里把文件**或文件夹**直接拖到输入框上即可填入绝对路径（拖动时输入框会高亮）。拖文件夹会填入文件夹本身；「链接文本」为空时自动用拖入项的名字填上，和你点「浏览…」选完的行为一致
- 所有**路径输入框**都支持拖拽：新增映射的「外部路径」、编辑映射的「目标路径」、重新指向的「手动指定」、文件浏览器的地址栏（拖文件夹进去 = 进入该目录）、设置里的「监控文件夹」（这一处只接受文件夹，拖文件会自动改用它所在的目录）
- 一次拖入多项时只取第一个，并弹提示说明
- 「导出 CSV」：把当前映射表导出到仓库根目录。针对表格软件不按逗号拆列的情况，改为 **Tab 分列 + UTF-16 LE + BOM（FF FE）+ CRLF**；不额外插入 `sep=` 行。首行直接是表头，字段内容中的逗号原样保留。扩展名仍为 `.csv`，文件内容按 Tab 分列。
- 「清空缓存」：清掉「文件名 → 磁盘路径」的查找缓存
- 面板底部可展开「最近变更」，记录每次改写的前后路径和原因

编辑器里还有命令 **「插入外部文件/文件夹链接」**，在光标处插入一条外部链接。

## 设置说明

### 监控的外部文件夹
这些目录会：① 被实时监听（文件增删改后自动核对链接）；② 作为「找新位置」的搜索范围。**强烈建议至少配一个**。

**插件只有这一个范围概念。** 找新位置、判断「范围内 / 范围外」，全部以「监控文件夹」为准。

### 范围内 / 范围外

面板里每一行链接都会被打上范围标记，判定标准只有一条：**这个链接指向的文件/文件夹，是否落在你配置的「监控文件夹」里。**

| 标记 | 含义 | 插件行为 |
| --- | --- | --- |
| **监控中**（+ 命中的文件夹名） | 落在某个启用的监控文件夹里 | 该目录的增删改会被实时监听 → 文件被改名/移动时插件**能发现**并给出推荐 |
| **范围外** | 扫描仓库时，笔记里确实存在这个外部链接，但目标不在任何监控文件夹里 | 不会被实时监听，也不会去那些位置找 → 文件改名/移动时插件**发现不了** |

面板顶部的范围筛选可以一键切到「监控文件夹内 (N)」或「监控文件夹外 (N)」，用来检查哪些引用还裸奔着。

> **「范围外」不是错误状态**，它只是一句实话：这个引用在你的监控范围之外，插件对它无能为力。想让它被监控，把它所在的目录加进「监控文件夹」即可。

### 范围不会蔓延（重要）
**插件只会在你配置的监控文件夹里搜索和监听。** 用户主目录、桌面、文档、下载等系统位置**永远不在范围内**。

这条规则是硬性的：
- 推荐列表里只会出现监控文件夹里的文件/文件夹
- 早期版本有两个会扩大范围的东西，都已移除：
  - `alsoSearchUserProfile`（默认 true）→ 把整个用户主目录纳入搜索。结果桌面上碰巧同名的文件会冒出来当候选，而且每改一个外部文件就要遍历一遍主目录（几千个目录 / 上万文件），把整个系统的文件操作都拖慢。
  - **「额外搜索目录」** → 只搜索、不监听。它让「搜索范围」和「监控范围」变成两套口径：面板显示「范围外」，点扫描时却又能从那里找到文件，自相矛盾。现已整体移除。
- 现在只剩一个范围：**监控文件夹**。

### 链接匹配规则（可配置）

插件用一条正则从 Markdown 里抓「外部链接」。这条规则在设置页里可以直接看、直接改。

**默认规则**：

```regex
(!?)\[([^\]\n]*)\]\(([^)\n]+)\)
```

匹配 `[文字](路径)` 和 `![文字](路径)`（嵌入）。

**捕获组约定**（改规则时最重要的一条）：

| 组 | 含义 |
| --- | --- |
| 第 1 组 | 前缀，用来判断是不是嵌入（是 `!` 就当嵌入） |
| 第 2 组 | 链接文字 |
| 第 3 组 | **目标路径**（必须有，否则这条匹配会被跳过） |

如果不想记位置，可以改用**命名捕获组**，顺序随意：

```regex
\((?<target>[^)\n]+)\)\[(?<text>[^\]\n]*)\]
```

上面这条把目标路径放在第 1 组也能正常工作，因为用的是名字而不是位置。

**设置页提供的东西**：

- 正则输入框 + 标志输入框（允许 `g i m s u`，`g` 会自动补上）
- 实时体检：✓ 规则有效（几个捕获组）/ ⚠ 取不到目标路径 / ✗ 规则无效 + 报错信息
- **「试一下」**：粘一段 Markdown 进去，实时列出每条命中的链接、解析出的目标路径，以及**它会不会被当成外部链接**（这一步和实际扫描走同一套判断，所以看到什么就是扫描时会得到什么）
- **「保存并重新扫描」** 和 **「恢复默认规则」** 两个按钮

**几个必须知道的边界**：

- **规则写坏不会让插件挂掉**：编译失败时自动退回默认规则，并在设置页显示红字、弹一条通知。面板顶部的扫描结果不会突然变空。
- **自定义规则只影响「识别 / 扫描」**。写回笔记时统一输出标准 `[文字](路径)` 形式 —— 也就是说，如果你加了一条匹配 `[[路径]]` 的规则，插件能认出来，但修好后会把它改写成 `[文字](路径)`。
- 规则能匹配空串（例如 `.*`）时会自动跳过空匹配，不会死循环；单篇笔记最多识别 5 万条，防止病态规则卡死。
- 带引号的 `[文字]("路径")` 是错误写法，默认规则**刻意不认**。真需要的话，自己改规则支持。

### 自动化
- **启用自动修复（总开关）** — 关掉后插件只读不写，连「待确认」都不会标
- **自动改写前需要我确认**（**默认开启**）— 外部文件改名/移动后，插件只在面板里把链接标成「待确认」，**绝不自己动你的笔记**；你点「确认更新」或「确认全部待确认项」才写。想恢复「高置信度直接改写」就关掉它
- **打开笔记时检查** — 打开一篇笔记时核对它的外部引用
- **外部文件变动时核对** — 监控目录有增删改时自动核对链接
- **笔记变动时刷新记录**
- **实时监控外部目录** — 部分网络盘不支持，会自动退化为非递归。监听回调**只入队**，不做任何文件操作
- **外部变动后的响应延迟**（默认 3000 ms）— 监控目录「安静」这么久之后才去核对链接。**批量改文件时把它调大**（比如 5000~10000），改文件期间插件完全不动作，改完才处理一批
- **定时全量扫描** — 分钟，0 = 关闭

### 「待确认」是什么
开着「自动改写前需要我确认」时，任何**自动触发**（外部变动 / 打开笔记 / 笔记变动 / 定时扫描）发现可以更新的链接，都只会把状态标成 **待确认**（蓝色徽章），笔记一个字都不动。

确认的三个入口：
- 面板行内 **「确认更新」** 按钮 —— 逐条确认
- 面板顶部 **「确认全部待确认项 (N)」** —— 一次性全确认
- 命令面板 **「确认全部『待确认』的外部引用更新」**

状态栏会显示 `外部引用 ⚠ 3（2 待确认）`；有新的待确认项时还会弹一条可点击的通知，点一下直接打开面板。

### 匹配策略
- **自动修复最低相似度**（默认 0.6）：只有分数达标才会自动改，低于阈值只提示
- **搜索最大深度 / 最大文件数**：控制遍历成本，防止卡顿

### 内容指纹（识别「只改了名、内容没变」）
- **启用内容指纹匹配** — 关掉后只能靠文件名 / 名称相似度
- **指纹算法** — SHA-256（推荐）/ MD5（更快）。切换会清空已有指纹重算
- **指纹最大文件大小** — 单位 MB，超过此大小不算指纹（默认 64，避免读超大文件）
- **清除全部内容指纹** — 显示当前已记录条数

### 路径处理
- **用户名变更时自动重映射** — `C:\Users\旧名\...` → `C:\Users\当前名\...`
- **盘符映射** — 每行 `D:=C:` 或 `D: -> E:`，用于换盘/换机器
- **POSIX 绝对路径根目录** — 只有以这些前缀开头的 `/xxx` 才当外部路径，避免把 Obsidian 的库内绝对链接误判成外部引用
- **路径含空格时用尖括号包裹** — 写成 `[文本](<C:\a b\c.txt>)`

### 记录与日志
- **写入变更日志** — 每次改写记一笔，默认写到 `.obsidian/plugins/external-link-manager/change-log.md`

## 相似度打分规则

三条策略并行跑，结果按路径去重后取最高分，最后按分数排序成推荐列表。

### 一、内容指纹一致 → 1.00（最强）

给链接引用到的外部文件记录 SHA-256 指纹。文件被改名后：

1. 先用**文件大小**把候选缩到极小集合（同大小才可能是同一个文件）
2. 再逐个算指纹比对，一致就是同一个文件

因为只对「链接引用到的文件」算指纹、且 `大小 + 修改时间` 没变就复用旧值，日常开销几乎为零。
**即使名字改成完全不相干的 `zzz-新名字.dat` 也能认出来。**

> 前提：该文件曾经被扫描到过（处于「正常」状态）从而留下了指纹。
> 如果文件在你第一次扫描之前就已经被改名，指纹这条路走不通，会退到下面两条。

### 二、文件名完全一致 → 0.35 ~ 1.00

文件名相同只是入场券（基础分 0.35），真正的证据是**父级目录路径的重合度**：

```
score = 0.35 + 0.65 × (匹配上的父级目录层数 / 旧路径的父级目录层数)
      + 0.3  （新旧目录互为父子，例如移进了子文件夹）
      + 0.03 （同一个盘符）
```

原路径 `C:\Users\me\Desktop\a.txt`：

| 新位置 | 分数 | 结果 |
| --- | --- | --- |
| `C:\Users\me\Desktop\a.txt`（原样） | 1.00 | 无需修复 |
| `C:\Users\me\Desktop\归档\a.txt` | 0.68 | 自动修复 |
| `C:\Users\me\Documents\a.txt` | 0.38 | 提示但不自动改 |
| `D:\下载\a.txt` | 0.35 | 提示但不自动改 |

### 三、名称相似（疑似改名）→ 0.35 ~ 1.00

文件名对不上，只能靠名称相似度。**文件和文件夹都参与**：

```
名称相似度：前缀关系 → 0.75 + 0.25 × (短名长度 / 长名长度)
            否则   → 1 - 编辑距离 / 长名长度
score = 0.35 × 名称相似度 + 0.65 × 父目录重合度 + 0.03（同盘符）
```

| 原路径 | 新位置 | 名称相似度 | 结果 |
| --- | --- | --- | --- |
| `D:\x\file1` | `D:\x\file11` | 0.96 | 自动修复 |
| `D:\x\更新jdk启动参数260921.txt` | `D:\x\更新jdk启动参数2609211.txt` | 0.97 | 自动修复 |
| `D:\x\file1` | `D:\x\file12` | 0.96 | 两个候选并列 → 人工确认 |
| `D:\x\file1` | `D:\other\backup` | 0.1 | 拒绝，不硬凑 |

改名匹配有**双重门槛**：名称相似度 ≥ 0.85 且父目录重合度 ≥ 0.5，两个都过才会成为候选。
另外先用「首字符一致 + 长度差 ≤ 8」做廉价预筛，所以即使监控目录里有几万个文件也不会卡。

### 自动 vs 手动

| | 条件 |
| --- | --- |
| **自动应用** | 状态为「可修复」且并列最高分唯一，且分数 ≥ `自动修复最低相似度`（默认 0.6） |
| **提示但不动手** | 分数不够，或有两个以上并列候选（状态「多个候选」） |

设计取向：**宁可少改，不可改错**。分数不够就列出来让你确认。

## 支持 / 不支持的写法

**支持**

- `[文本](C:\绝对\路径.txt)`、`[文本](C:/正斜杠/路径.txt)`
- `[文本](<C:\含 空格\路径.txt>)`（Markdown 规范的尖括号）
- `[文本](\\server\share\file.txt)`（UNC）
- `[文本](file:///C:/Users/x/a.txt)`
- `![图片](C:\x\a.png)`（嵌入语法）
- POSIX 绝对路径（macOS / Linux），需落在「POSIX 根目录」白名单内
- 指向文件夹（没有扩展名的路径）
- 修复时**保持原写法风格**（反斜杠 / 正斜杠 / file:// URI / 尖括号）

**不支持**

- **带引号的写法 `[文本]("C:\路径.txt")`** —— 引号会被当成路径的一部分，Obsidian 自己点开也打不开，属于错误写法。插件**刻意不兼容**，这类链接会被直接忽略（既不会被扫描到，也不会被改写）。遇到请手工改成 `[文本](<C:\路径.txt>)` 或裸路径
- 引用式链接定义 `[文本][ref]` + `[ref]: C:\...`
- HTML 标签 `<a href="C:\...">`
- 纯文本里裸写的路径（没有 `[]()` 包裹）

**不会误判**

- `http(s)://`、`mailto:`、`obsidian://` 等带 scheme 的链接
- 指向仓库内部的绝对路径
- Windows 下 `/开头` 的路径（视为 Obsidian 库内绝对链接）

> 以上「支持 / 不支持」都取决于当前的**链接匹配规则**。规则在设置页里可看可改（见 [链接匹配规则](#链接匹配规则可配置)），默认规则就是按上表设计的。

## 安全设计

- **精确匹配才写**：改写时先在笔记里查找完整的 `[文本](原路径)` 字面量；找不到就按行号附近找；再找不到就**放弃并提示**，绝不瞎猜
- **不重复写**：内容无变化时不会触发写入
- **不会自触发死循环**：插件写入时标记该笔记，忽略自己触发的变更事件
- **可追溯**：每次改写都记入「最近变更」和可选的变更日志文件
- **可整体关闭**：`启用自动修复` 关掉后，插件只读不写
- 改写前建议先 `git commit`（你的仓库本来就有 obsidian-git）

## 不干扰外部文件的正常读写

监控本身绝不该拖慢你改文件。为此做了这些事：

| 措施 | 说明 |
| --- | --- |
| **监听回调零开销** | `fs.watch` 的回调只做一件事：把 `{路径, 文件名, 时间}` push 进一个内存数组。不 `stat`、不 `readdir`、不 hash、**不加锁、不打开任何文件** |
| **无锁事件队列** | 处理时用 `splice` 一次性取走整批（JS 单线程，原子操作），处理期间新到的事件进新队列，下一轮再处理。**既不丢事件，也不互相阻塞**，更不存在「正在扫描中，本次请求被丢弃」 |
| **搜索范围只限监控目录** | 不会去遍历用户主目录 / 桌面 / 文档，磁盘 I/O 天然受限 |
| **变动核对不重读笔记** | 外部文件变了，笔记内容没变 —— 只复用已解析的记录重新判定，一次 `cachedRead` 都不做 |
| **只搜发生变动的那个文件夹** | 改 A 目录的文件，不会去翻 B 目录 |
| **自动检测默认只标记，不写盘** | 「自动改写前需要我确认」默认开启，自动检测绝不写笔记，等用户点确认 |
| **限流落盘** | 扫描结果最多每 5 秒写一次 data.json（那个文件可能有几百 KB），不再每个事件写一次 |
| **全程异步 + 时间片让出** | 目录遍历和 `stat` 都用异步 API，每 16 ms 让出主线程，不冻结 Obsidian 界面 |
| **不持有文件句柄** | 算指纹用流式读，读完立即关闭；文件被占用 / 改名时自动降级为「无指纹」而不是报错 |
| **自动路径更严的上限** | 自动核对时最多遍历 5000 个文件（手动扫描用你配置的上限），批量操作时更不容易抢磁盘 |

> 插件**没有任何文件锁**。它从不独占打开文件、不写 `lock` 文件、不做 `flock`/`LockFile` 之类的操作。
> 唯一会写的地方是你自己的 Markdown 笔记（而且默认还要你确认），以及插件目录下的 `data.json` / `change-log.md`。

### 还是觉得卡？
1. 把 **自动改写前需要我确认** 保持开启（默认就是开的）—— 这样插件连写盘都省了
2. 把 **外部变动后的响应延迟** 调到 `5000` ~ `10000`
3. 确认 **监控的外部文件夹** 里没有放超大目录（例如整个 `D:\`）
4. 如果只是偶尔需要核对，直接关掉 **实时监控外部目录**，改用「打开笔记时检查」+ 手动点「扫描」
5. 还是卡的话，先把插件整个关掉再测一次 —— 这样能立刻区分是插件问题还是系统本身（杀软实时扫描、图标缓存、云同步客户端等）的问题

## 开发者：测试

`dev/` 下是几个免依赖的 Node 脚本（用 mock obsidian + 真实文件系统，**不需要装任何 npm 包**）：

| 脚本 | 用途 |
| --- | --- |
| `run-test.js` | **主回归测试：137 项通过 / 0 失败 / 1 段跳过**；覆盖扫描 / 修复 / 匹配 / 设置迁移 / CSV 编码 / 拖拽填路径及待确认流程 |
| `audit-vault.js` | 只读扫描真实仓库，输出外部引用清单（不写任何文件） |
| `probe-path-settings.js` | 打印「路径处理」各项设置在当前平台上的实际生效情况 |
| `clean-data.js` | 一次性维护脚本：清理 `data.json` 里的遗留缓存（**会写文件**） |

跑测试（部分沙箱环境需要把临时目录指到仓库内）：

```bash
mkdir -p ./.tmp && TMPDIR=./.tmp node dev/run-test.js
```

验证某个历史版本（回退点）能不能跑：

```bash
ELM_PLUGIN=/path/to/old/main.js node dev/run-test.js
```

体检自己的仓库：

```bash
node dev/audit-vault.js "D:\Notes\my-vault" "D:\资料"
```

> 测试脚本比被测版本新时，那个版本没有的能力会被**整段跳过**并单独计数，不会误报失败。
